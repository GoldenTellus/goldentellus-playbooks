# 🤖 Codex 案例拆解 SOP

本 SOP 用于把经授权、已脱敏的 AI 应用落地素材沉淀为实践层内容。它适用于 `/case-new`、`/case-update {id}`，以及“拆解这个案例”等自然语言请求。

## 1. 接收与发布授权

先检查以下四类素材：业务背景、技术方案、实施过程、结果数据。至少具备三类才进入结构化拆解；缺失内容继续追问，不以想象补齐。

发布前必须确认：

- 素材已去除客户、个人、账号、订单、精确地址、截图、日志、原始数据和密钥等可识别信息；
- 他人案例已经获得公开授权，自有案例已明确公开范围；
- 用户明确同意本次内容可公开发布。

未通过以上任一项，不向公开仓库提交，不创建公开 Issue 或 Project 卡片。

## 2. 六段拆解

| 阶段 | 必须回答的问题 |
|---|---|
| 诊断 | 业务背景、痛点、需求、成功标准是什么？ |
| 架构 | 技术选型、架构和成本取舍是什么？为什么？ |
| 开发 | 实施时间线、关键决策、代码要点和踩坑是什么？ |
| 数据 | 数据来源、清洗、结构、质量问题和边界是什么？ |
| 集成 | 对接、部署、监控、告警和回滚如何设计？ |
| 运营 | 结果口径、反馈、迭代方向和可复用性是什么？ |

每段必须写出“关键决策”和“为什么”。信息不足写 `[待补充]`，完全不涉及写 `[不适用]`。效果数据必须标示为已测量、客户提供、估算或推断。

## 3. 分流规则

| 条件 | 目标仓库 | 处理方式 |
|---|---|---|
| 经授权的完整案例叙事 | `goldentellus-cases` | 必须写入；正文唯一存于 `by-industry/<industry>/` |
| 方案足够具体且用户允许生成演示实现 | `goldentellus-demos` | 建立使用模拟或授权数据的最小 Demo，并声明“演示用途” |
| 可复用 SOP、模板或检查清单 | `goldentellus-playbooks` | 新建或补充相应流程资产 |
| 通用脚本、计算器、分析器或脚手架 | `goldentellus-toolkit` | 提供输入、输出、限制、测试和使用说明 |
| 已核实的新外部资源 | `awesome-fde` | 检查链接、许可证、维护状态和重复项后追加 |
| 多来源支撑的行业观察 | `goldentellus-reports` | 标注来源、采集时间、样本限制和结论边界 |

单一案例不自动产生行业趋势。案例分类的唯一真源是 frontmatter；阶段和难度目录只增加指向行业目录正文的索引链接，不复制正文。

## 4. 发布与完成

发布前，Codex 展示目标仓库、文件、分类、关联和待补充项。获得本次发布确认后，分别直接提交到各仓库 `main`，提交信息使用 `feat(cases): add CASE-<编号> <标题>` 等约定。

发布后：

1. 运行格式、构建和链接检查；
2. 在对应公开 Project 中创建仅含标题和公开链接的卡片，并设为“已发布”；
3. 报告每个仓库的提交结果；
4. 建议可从案例提炼的理论方向。只有用户确认后，才进入理论分析 SOP。
